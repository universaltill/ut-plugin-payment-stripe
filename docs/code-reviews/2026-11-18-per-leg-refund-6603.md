# Review: per-leg refund_amount (ut-docs#6603), Stripe v1.8.0

Card: universaltill/ut-docs#6603 (plugin part). Design: architect note on the card. ADR-0196 d.4 is applied as written, so no ADR is needed.

## What shipped
- `origPayment.RefundAmount *int64` (`src/host.go`). It is presence-aware, so an absent field is not read as 0.
- `src/refundlegs.go`: `perLegMode` (non-reversal, and at least one leg carries `refund_amount`), `planLegs` (validates the whole split before any call) and `refundLegs`. `refundLegs` refunds each leg's own amount in payload order, stops at the first failure, returns `refund_partial` once a leg is done, and otherwise returns the leg's own reason.
- Per-leg Idempotency-Key `ut-refund-<evt>-<pi>-<refund_amount>`. The legacy key `ut-refund-<evt>-<pi>` and the legacy path are unchanged when the field is absent, and for reversals.
- Manifest 1.7.0 → 1.8.0. README and CLAUDE.md are updated, and so is the ut-docs `reference/payment-provider-contract.md` row.

## Review
The Dev was Sonnet. Opus did this independent review. Verdict: **approve after fixes**. There are no must-fix findings in the plugin.

Checked and clean:
- **No double refund on retry.** The same event id always carries the same allocation, because core hashes the payload including `refund_amount`. Done legs are re-sent with identical key and params, so Stripe replays them.
- **No v1.7.0 key clash.** The amount in the key avoids `idempotency_error`.
- **Key length.** Core caps the attempt id at 128, so the key is at most about 205 characters, under Stripe's 255.
- **No leg picking or "next leg" fallback.** Over-refund stays bounded per charge by Stripe.
- **Validation before any call.** A leg must be > 0 and ≤ amount + tip, the sum must equal the total, a ref must be present, there are at most 16 legs, and overflow is checked.
- **Logs.** They use `maskRef` and `scrubRefs` only, never Stripe's message.
- **Reversals and the legacy path are untouched.** `refundOne` is only re-plumbed for the key.

Findings:
- **F1 (major, accepted → ut-docs#6648; regression vs today, flag on that card):** a *second* partial refund of a split sale now declines where v1.7.0 succeeded. Example: legs 3000/2000, with 2000 already refunded from leg A, then a further 2000. Core allocates from leg A again without netting earlier refunds, so A answers `amount_too_large` and per-leg mode stops. v1.7.0's big-first would have moved to B. Nothing is over-refunded, because it fails closed. The real fix is core's per-leg netting (#6648). That card should note this regression and get its priority raised.
- **F2 (minor, covered by ut-docs#6647):** if core's leg order changed between two attempts with different event ids, a partial could over-refund. Example: 4000 on 3000/2000, attempt 1 A,B with B failing, attempt 2 B,A, so B 2000 and A fails, for 5000 back. With a stable order the plugin is safe: every non-last leg is a full leg in core's allocation, so a fresh event meets Stripe's `charge_already_refunded` on the done leg first. Stable order is already #6647.
- **F3 (minor, fixed):** the README told the cashier to tap Refund again after `refund_partial`. Stripe replays a stored definite refusal under the same key, so a retry only helps after a network or temporary error. The README now says so and points to the Dashboard for the rest.
- **F4 (minor, fixed):** a mutant that removes the sum-overflow guard survived, because the existing "overflow" case is also caught by `sum != amount`. Added `TestLegsSumOverflowGuard`, where the wrapped sum equals `p.Amount`. It goes red with the guard removed and green with it in place. The `amount+tip` overflow guard is equivalent to `r > whole` (a wrapped negative), so it gets no extra test.
- **F5 (info):** `refundLeg.Full` is unused on the Stripe side, because Stripe is stateless. Harmless, and it is kept for symmetry with SumUp.
- Known and accepted, not re-raised: core shows a generic decline for `refund_partial` (#6647), and Stripe's key window is at least 24 hours (README).

## Verification
- **Tester:** 19 mutants, with 18 killed (the survivor is fixed in F4). A driven run of the real built wasm in a universal-till `WasmRuntime` harness covered two legs, a partial then a retry, and an invalid split.
